Contexto

O mercado de salões de beleza

📊

Setor em crescimento

O Brasil é o 4º maior mercado de beleza do mundo, com mais de 1 milhão de salões ativos. A maioria são micro e pequenas empresas familiares.

📆

Gestão ainda manual

Estima-se que 70% dos pequenos salões ainda usam agenda de papel, WhatsApp ou planilhas para controlar horários, clientes e finanças.

💸

Perda de receita

Agendamentos manuais geram ~30% de ausências (no-shows). Sem lembretes automáticos, cada falta é uma perda direta de faturamento.

🧏

Exclusão digital

Profissionais e clientes surdos não encontram sistemas de gestão com suporte a Libras — uma barreira real de inclusão no mercado de trabalho.

Problema

Qual problema real resolvemos?

⚠ Agendamento ineficiente

Clientes precisam ligar ou mandar WhatsApp. O salão controla por papel. Conflitos de horário, falta de confirmação e ausências são constantes.

⚠ Controle financeiro frágil

Receitas e despesas anotadas em cadernos. Sem visão de lucro real. Sem registro do que foi pago, como foi pago, quem pagou.

⚠ Estoque sem gestão

Produtos acabam sem reposição. Não se sabe o custo real dos produtos vendidos. Não há vínculo entre produto usado e atendimento.

⚠ Barreira de comunicação

Nenhum sistema de gestão para salões oferece recursos em Libras. Profissionais surdos e clientes surdos ficam excluídos do mercado.

Decisão Técnica

Por que tRPC e não REST?

⚡ tRPC — TypeScript Remote Procedure Call

Em vez de definir manualmente endpoints HTTP, códigos de status, contratos de request/response e documentação Swagger, o tRPC permite que o frontend chame funções do backend como se fossem locais, com segurança total de tipos.

✘ Abordagem REST tradicional
Definir manualmente cada endpoint · Documentar com Swagger/OpenAPI · Gerar cliente HTTP com fetch/axios · Tipar manualmente as respostas · Sem sincronização automática de tipos entre front e back
✔ Abordagem tRPC
Procedures tipadas no servidor · Cliente importa tipos direto do servidor · Batch automático de chamadas · Validação Zod integrada · Erro de tipo = erro de compilação, nunca em produção
Decisão Técnica

Por que Drizzle ORM e não Prisma?

🗄 Drizzle ORM — TypeScript-first, zero abstração

O Drizzle foi escolhido por ser um ORM que gera SQL otimizado sem engine binária, resultando em performance superior e bundle menor — crucial para deploy serverless e Docker.

✘ Prisma
Engine binária (~6MB) · Cold start lento · Sintaxe própria (não SQL) · Migrations com shadow database · Mais pesado para bundles serverless
✔ Drizzle ORM
Cliente TypeScript (~300KB) · Queries SQL-like familiares · Relações definidas explicitamente · Migrations com drizzle-kit · Ideal para Node.js e edge runtimes
Decisão Técnica

Por que PWA e não App Nativo?

📱 PWA — Progressive Web App

Uma PWA é uma aplicação web que pode ser instalada como app nativo no celular, com ícone na tela inicial, splash screen, funcionamento offline e notificações push — sem precisar publicar na Google Play ou App Store.

✘ App Nativo (Flutter / RN)
Duplicar código (web + mobile) · Duas bases de código · Aprovação em lojas · Atualizações via loja · Curva de aprendizado adicional
✔ PWA (vite-plugin-pwa)
Único código para web e mobile · Instalável como app nativo · 56 assets offline · Atualização silenciosa via SW · Usado por Twitter, Pinterest, Uber, Starbucks
Decisão Técnica

Por que Monolito e não Microsserviços?

🏗 Monolito Fullstack

Para o escopo do projeto integrado, um monolito bem estruturado oferece o melhor equilíbrio entre simplicidade de desenvolvimento, deploy e manutenção. A separação lógica em camadas (shared/ server/ client/) garante que uma migração futura para microsserviços seja possível sem reescrever o código.

✘ Microsserviços (não adotado)
Alta complexidade operacional · Latência de rede entre serviços · Orquestração (Kubernetes) · Complexidade de deploy · Overhead para equipe pequena
✔ Monolito bem estruturado
1 comando = deploy completo · Comunicação interna sem latência · TypeScript garante consistência · Dockerfile multi-stage ~200MB · Migrável para microserviços no futuro

Planejamento

Riscos iniciais e mitigações

📱

Responsividade em todos os dispositivos

Risco: Interface não adaptar em telas pequenas. Mitigação: Tailwind CSS responsivo, sidebar adaptativa (overlay em mobile), testes em breakpoints reais.

🌐

PWA — Cache e Offline

Risco: Service Worker não cachear corretamente. Mitigação: Workbox (Google) com estratégia Network First + Precaching. 56 assets pre-cacheados.

🧏

Qualidade do conteúdo em Libras

Risco: Imagens imprecisas ou vídeos bloqueados. Mitigação: Fotos reais validadas. Links diretos YouTube (abrem nova aba) ao invés de iframes embedados.

🔐

Vazamento de dados

Risco: Exposição de dados de clientes e financeiros. Mitigação: bcrypt + JWT + Helmet + rate limiting + CORS + sanitização + trilha de auditoria.

⚡

Performance com volume de dados

Risco: Dashboard lento com muitos agendamentos. Mitigação: Cache em memória (10min), índices compostos, React Query staleTime, exportação assíncrona.
